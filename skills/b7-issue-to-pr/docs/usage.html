Pipeline autonomo issue → PR

Cómo usar los skills b1-add-worktree, b7-issue-to-pr, b8-swarm, b9-close y b10-ship para llevar un issue de GitHub a un PR mergeado de forma reproducible y con guardarraíles.

1 Vision general

Tres skills compuestos. Cada uno hace una sola cosa, y los superiores reutilizan los inferiores. La regla de oro: nunca duplicar logica entre skills; si necesitas triage, llamas a b1-triage-issue; si necesitas un worktree, llamas a b1-add-worktree; etc.

SkillEstadoQue haceCuando se invoca
b1-add-worktree listo Crea un git worktree aislado con symlinks de .env*, puerto dev libre y dev.sh. Manual (/b-add-worktree) o automatizado con --headless.
b7-issue-to-pr listo Pipeline issue → PR completo: triage con plan[], worktree, sticky comment, build+screens, commit, PR draft, b6-pr-review, labels sincronizadas. Manual con un número de issue, o headless via claude -p.
b9-close listo Cierre del feature: higiene (format, autofixer, lint, type-check, comentarios), validación del plan, code-quality sub-agent, CHANGELOG idempotente, merge. Tras b7 o al cerrar un feature manual con tasks.json.
b8-swarm listo Orquestador secuencial sobre el backlog ready,auto-pr. Drena hasta --max=N issues corriendo b7 uno por vez (no paraleliza). Lock propio, kill-switch b8.STOP, dwell entre runs, hereda backpressure de b7. No mergea PRs. Manual (/b8-swarm --max=3) o headless via claude -p desde cron/launchd.
Modo por defecto b7 corre en --wet por defecto: triage → worktree → build → commit → PR draft → b6-review. --dry-run sigue disponible para inspeccionar antes de commitear. Los presupuestos (iteraciones, archivos, líneas) y los guardarrailes (lock, kill-switch, backpressure, denylist) siguen activos en ambos modos.

2 Diagrama del flujo

Lo que pasa cuando se invoca b7-issue-to-pr 142 (default --wet).

0
preflight + lock
1
b1-triage-issue (genera plan[])
2
b1-add-worktree --headless
3
sticky comment (started)
4
b2-build-feature + b7-screen-review (loop)
5
plan-check + DoD gates
6
b3-git-commit
7
b4-pull-request --draft
8
b6-pr-review
9

Tras el run, el cierre normal es invocar b9-close sobre el worktree para higiene final + merge a master (idempotente con el CHANGELOG que b7 ya escribió).

En --dry-run se ejecutan los pasos 0–5 (build + DoD), se omiten commit/PR/review, y el worktree queda intacto para inspección manual. La label del issue va a in-progress pero no a in-review.

3 b1-add-worktree

Crea un git worktree con todo lo necesario para correr ./dev.sh sin chocar con el repo padre ni otros worktrees.

Uso interactivo

/b-add-worktree feat/142-mi-feature

El skill confirma el nombre de rama, pregunta la base (rama actual o master) y corre el script.

Invocacion directa del script

bash ~/.claude/skills/b-pipeline/skills/b1-add-worktree/scripts/setup-worktree.sh \
  feat/142-mi-feature master

Modo headless (para automatizacion)

bash ~/.claude/skills/b-pipeline/skills/b1-add-worktree/scripts/setup-worktree.sh \
  feat/142-mi-feature master --headless

En headless el script no abre iTerm2 y emite como ultima linea de stdout un formato parseable:

WORKTREE_READY dir=~/www/your-project/worktrees/142-mi-feature branch=feat/142-mi-feature port=6027

Los consumidores (b7) deben hacer grep '^WORKTREE_READY ' en lugar de re-parsear el log humano.

Que hace por dentro

  1. Verifica que el working tree del repo padre este limpio (aborta si no).
  2. git worktree add con la rama nueva.
  3. Symlinkea todos los .env* del repo padre.
  4. Detecta el primer puerto libre desde 6026 hacia arriba.
  5. Genera dev.sh con ese puerto (no edita package.json).
  6. pnpm install --frozen-lockfile.
  7. Abre nueva ventana de iTerm2 (omitido en headless).
Recordatorio Adentro del worktree corres ./dev.sh, NO pnpm dev (este ultimo esta hardcoded a 6025 y choca con el padre).

4 b7-issue-to-pr

Glue skill que encadena 9 pasos no-saltables para llevar un issue a un PR draft con review adjunto. El valor está en la orquestación + budgets + rastro documental triple (CHANGELOG + sticky issue comment + PR body) coordinado por publish-docs.sh.

Argumentos

<issue> [--dry-run | --wet] [--max-iterations=N] [--budget-files=N] [--no-pr]
        [--no-screens] [--screens-only] [--lang=es|en] [--directives="<texto>"]

Defaults: --wet, --max-iterations=6, --budget-files=25, screens habilitadas, --lang autodetectado del issue.

Los 5 pasos obligatorios (no se saltan nunca)

  1. Worktree via b1-add-worktree --headless. Branch feat/<N>-<slug> o fix/<N>-<slug>. Prohibido editar el repo principal.
  2. Sticky comment en el issue (marker <!-- b7:status -->) via publish-docs.sh issue-comment. Se edita en cada paso, no se duplica.
  3. Commits via b3-git-commit — conventional commits agrupados por tema.
  4. PR draft via b4-pull-request con cuerpo de publish-docs.sh pr-body (Closes #N, release notes, screenshots). Labels: ready/auto-pr → in-progress → in-review.
  5. b6-pr-review sobre el PR recién abierto. Findings de severidad alta bloquean.

Plan estructurado (plan[]) y DoD

El triage genera un plan[] en .b7/triage.json con items {id, desc, done, note?}. Cada sub-agente que completa un ítem debe marcarlo:

~/.claude/skills/b-pipeline/skills/b7-issue-to-pr/scripts/publish-docs.sh plan-done <id> --worktree <wt>

El gate de Definition of Done corre publish-docs.sh plan-check — exit 0 si todos los items están done (o el plan está vacío), exit 5 si quedan pendientes. El run no es válido hasta que pase.

Subcomandos de publish-docs.sh

SubcomandoHace
started / iter / doneVariantes del sticky comment según el estado del run.
changelogAppendea entry idempotente a CHANGELOG.md bajo [Unreleased]. Detecta (#N) existente y skipea.
pr-bodyEscribe .b7/pr-body.md que consume b4-pull-request.
allplan-render + changelog + pr-body + issue-comment.
plan-render / plan-done / plan-checkGestión del plan[] estructurado.
aborted / bailedCierre con ⛔ / 🚪 en el sticky cuando el run se detiene.

Frases prohibidas al cerrar

Estas frases significan "abandoné a mitad de camino". Si el modelo las escribe, el run no terminó — debe ejecutar el paso pendiente:

  • "Ready for b3-git-commit + b4-pull-request"
  • "Listo para commit / Listo para PR"
  • "Pendiente: abrir PR / correr review"
  • "Próximos pasos: <algo del pipeline>"

Invocacion interactiva

Usa el skill b7-issue-to-pr con argumentos: 142 --dry-run

Claude leera el SKILL.md y ejecutara los pasos en orden, llamando a b1-triage-issue, b1-add-worktree, b2-build-feature, etc.

Después del run (cierre normal)

En --wet: PR draft abierto + b6-review adjunto + labels sincronizadas + sticky con link al PR. El cierre del feature lo hace b9-close en un paso aparte (higiene + merge a master).

En --dry-run: worktree con commits opcionales, label in-progress, sticky actualizado. Para promover: /b3-git-commit + /b4-pull-request; para descartar: git worktree remove.

5 b8-swarm listo

Orquestador secuencial de runs de b7. Una sola cosa: tomar issues del backlog ready,auto-pr y correr b7 sobre cada uno, uno por vez, hasta --max=N o hasta vaciar el backlog. No paraleliza, no mergea, no edita issues fuera de lo que ya hace b7.

Decisiones de diseño tomadas

PreguntaDecisión
Workers paralelos vs colaCola secuencial. Paralelo quemaba contexto+tokens y duplicaba coordinación (lock, backpressure) que b7 ya resuelve.
Granularidad del clusterNo hace clustering. Como es secuencial, el overlap de archivos no importa: cada b7 hace su worktree+rama+PR aislado.
Merge en el loopNo. b8 deja PRs draft + b6-review por PR. Humano mergea. b9-close también queda manual.
Integration test post-waveNo. Cada b7 ya corre b6-pr-review individual; CI sobre master cubre el check cruzado al mergear.
BackpressureHereda B7_MAX_OPEN_PRS. Si la cola está llena al iniciar o entre runs, b8 detiene la ola.

Argumentos

[--max=N] [--issues=N1,N2,...] [--dry-run] [--on-error=continue|abort]
[--dwell=SECONDS] [--label=ready,auto-pr]

Defaults: --max=5, --on-error=continue, --dwell=10, --label=ready,auto-pr.

Invocación

# manual (sesión Claude):
"corré b8-swarm con max=3"

# headless / cron / launchd:
claude -p --permission-mode acceptEdits \
  "Usa el skill b8-swarm con argumentos: --max=3"

# headless con lista explícita:
claude -p --permission-mode acceptEdits \
  "Usa el skill b8-swarm con argumentos: --issues=142,143,150"

Flujo de la ola

  1. Preflight: b8.STOP ausente, b8.lock libre, gh auth ok, working tree limpio, backpressure ok.
  2. Construye cola: gh issue list --label "$LABEL" --state open, filtra do-not-automate y <!-- no-auto-pr -->, trunca a --max.
  3. Por cada issue: verifica kill-switch + backpressure → invoca b7-issue-to-pr → anota resultado en b8-runs/<stamp>.md → sleep $DWELL.
  4. Cierra ola: libera lock, reporte agregado con outcomes + URLs de PRs creados.

Kill-switch propio

# detener la ola antes del próximo b7 (no mata el b7 en curso):
touch "$CLAUDE_PROJECT_DIR/b8.STOP"
rm "$CLAUDE_PROJECT_DIR/b8.STOP"

Variables de entorno propias

VariableDefaultPara qué
B8_MAX_PER_WAVE5Max issues por ola si no se pasa --max.
B8_DWELL_SECONDS10Espera entre invocaciones de b7.
B8_DEFAULT_LABELready,auto-prLabel query del backlog.
Por qué no paraleliza Workers paralelos con claude -p chocan con el b7.lock (que es por-proyecto, no por-issue) y rompen el contador de backpressure. Si en algún momento hay capacidad real para paralelo (lock por-rama, claude -p sin overhead), iría en un skill separado b9-swarm-parallel, no acá.

6 Guardarrailes y kill-switches

Pre-commit budget hook

El hook ~/.claude/skills/b-pipeline/skills/b7-issue-to-pr/hooks/pre-commit-budget.sh se instala automaticamente en cada worktree (lo hace setup-worktree.sh via core.hooksPath con scope por-worktree, encadenando al pre-commit previo del repo — husky/lefthook — para no romper lint-staged). Rechaza commits que toquen paths de la denylist:

  • package.json, pnpm-lock.yaml, package-lock.json, yarn.lock
  • .env y .env.*
  • *.pem, *.key, secrets/**
  • svelte.config.js, vite.config.*
  • infra/**, .github/workflows/**, scripts/*.sh

Tambien rechaza el commit si la branch entera supera el cap de archivos (B7_BUDGET_FILES). Override solo manual con B7_BUDGET_OVERRIDE=1.

Kill-switch file

# detener cualquier b7 futuro de forma inmediata:
touch ~/.claude/projects/<your-project-slug>/b7.STOP

# permitir que vuelva a correr:
rm ~/.claude/projects/<your-project-slug>/b7.STOP

Lock concurrente

Solo una corrida de b7 a la vez. El lock vive en <state-dir>/b7.lock y guarda el PID. Locks viejos (PID muerto) se limpian solos en el preflight.

Backpressure

Si ya hay 3 PRs abiertos con label auto-pr-bot, el preflight aborta. Ajustable con B7_MAX_OPEN_PRS. Esto evita que el bot inunde el queue de revisión.

Opt-out por issue

Para que b7 ignore un issue concreto, agrega cualquiera de:

  • label do-not-automate
  • el comentario HTML <!-- no-auto-pr --> en el body
Lo que el bot NUNCA hace
  • commit con --no-verify
  • git push --force a ninguna rama
  • tocar lockfiles, package.json, .env*, CI configs
  • cerrar/mergear PRs (solo abre drafts)
  • auto-crear usuarios/permisos (recordatorio: identidad, acceso y permisos viven en capas separadas)

7 Invocacion headless

Para correr b7 desde cron, launchd, GitHub Actions o un script de polling.

Dry-run manual

claude -p --permission-mode acceptEdits \
  "Usa el skill b7-issue-to-pr con argumentos: 142 --dry-run"

Wet (default)

claude -p --permission-mode acceptEdits \
  "Usa el skill b7-issue-to-pr con argumentos: 142"
# default es --wet: commit + PR draft + b6-review

Polling de issues listos

Patron recomendado: un script externo que pida los issues con label ready,auto-pr y, si encuentra al menos uno, invoca b7.

# pseudocodigo (cron / launchd cada 15 min):
ISSUE=$(gh issue list --label ready,auto-pr --json number \
        --jq '.[0].number')
if [ -n "$ISSUE" ]; then
  claude -p --permission-mode acceptEdits \
    "Usa el skill b7-issue-to-pr con argumentos: $ISSUE --dry-run"
fi

8 Troubleshooting

"preflight: another b7 run is in progress (pid N)"

Hay un b7.lock con PID vivo. Si estas seguro que ningun proceso esta corriendo, mata el PID o borra el lock:

rm ~/.claude/projects/<your-project-slug>/b7.lock

"working tree is dirty"

El repo padre tiene cambios sin commitear. b7 aborta porque git worktree add requiere un tree limpio. Commit, stash o descarta tus cambios primero.

"X open auto-pr-bot PRs — at or above B7_MAX_OPEN_PRS"

Cola llena. Drena PRs (mergeando o cerrando) antes de que b7 abra mas. Esto es por diseño.

El worktree quedo huerfano tras un dry-run abortado

cd ~/www/your-project
git worktree list                   # ver cuales estan
git worktree remove ../worktrees/<dir> --force
git branch -D <branch>

Ver el ultimo run report

ls -t ~/.claude/projects/<your-project-slug>/b7-runs/ \
  | head -1 | xargs -I{} cat ~/.claude/projects/<your-project-slug>/b7-runs/{}

Verificar sintaxis de los scripts

bash -n ~/.claude/skills/b-pipeline/skills/b7-issue-to-pr/scripts/run.sh
bash -n ~/.claude/skills/b-pipeline/skills/b7-issue-to-pr/scripts/guardrails.sh
bash -n ~/.claude/skills/b-pipeline/skills/b7-issue-to-pr/hooks/pre-commit-budget.sh
